このアプリは何で、どう出来ているか

レシピを保存して家族で共有する Web アプリ。ログイン不要の「ゲスト」でも試せて、 登録するとチーム単位でレシピを共有できる。この資料は、実装済みのコードが 実際にどうなっているかと、なぜそうなっているかを 一通り追えるようにまとめたもの。

この資料の位置づけ 詳細な根拠はリポジトリ内の docs/design.md（設計書・約800行）にある。 このサイトはその要約と地図で、各所に § 付きで設計書の対応節を示している。 設計書が正、このサイトは読みやすさ優先の入口。

まず1つだけ覚えること

すべてのデータは teamId を持ち、認可は「その teamId と 同名の Cognito グループに所属しているか」の1問に還元される。

この規則がアプリ全体を貫いている。ここから外れる例外を作った時点で、この設計は壊れる。（§1.2）

この1本の規則を成立させるために、いくつもの「一見すると素直でない」選択がなされている。 たとえば 個人ユーザーも「メンバー1人のチーム」として扱う。 個人モードとチームモードを分ければ認可ルールが2本になり、分岐した瞬間にこの設計は成立しなくなるため。

ゲストが登録すると、localStorage のデータはクラウドへ引き継がれる（§5.3）。 「試してから登録する」までの体験が途切れないことを、この設計はかなり真面目に優先している。

技術スタック

層採用技術役割・選定理由
フレームワーク Next.js 16（App Router）
React 19 / TypeScript 5		 実態は「Next.js の上に載った SPA」に近い。データ取得はほぼクライアント側で行い、サーバー機能は /team を守る middleware だけに使っている（§3.4）
スタイリング Tailwind CSS v4 + daisyUI 5 v4 は tailwind.config.js を使わず、CSS 側（@plugin "daisyui"）で設定する。テーマは daisyUI 組み込みの4種をそのまま使い、独自テーマを定義しない（§6.1）
バックエンド定義 AWS Amplify Gen 2（CDK ベースの TypeScript IaC） インフラはすべて amplify/ 配下の TypeScript から生成する。CloudFormation の手書きや AWS コンソールでの手作業は行わない
認証 Amazon Cognito User Pool メールアドレス＋パスワード。チーム＝Cognito グループとして表現する。カスタム属性は一切使わない（§6.2）
API AWS AppSync（GraphQL） Amplify Data がスキーマから自動生成する。認可も同じスキーマ定義に書く
データベース Amazon DynamoDB Amplify Data 経由。部分一致検索が苦手という制約が、クライアント側検索という判断に直結している（§1.5）
サーバー処理 AWS Lambda ×2 Cognito グループ操作は Admin API でしかできず、ブラウザから実行できないため（§2.2）
テスト Vitest 単体テストと、実デプロイに対する認可の統合テストの2本立て（§10）
CI GitHub Actions ×2 無料の CI は常時、AWS を使う高価な CI はラベル opt-in ＋ main への保険（§10.4）
パッケージ管理 pnpm（バージョン固定） package.json の packageManager で固定。npm / yarn は使わない

ゲストの線は AWS に届いていない。これは手抜きではなく、 Amplify の allow.guest() がゲスト同士のデータを分離できないという制約への対応で、 未認証 Identity 自体を backend.ts で無効化して経路ごと塞いである（§5.1）。

続きの読み方

構成と動き → 画面を開いてから表示されるまでに何が起きるか。Repository による差し替え、画面一覧、データ取得の方針。 データと認可 → 4つのモデルと認可ルール。サインアップ・チーム参加・離脱・自己修復のフロー。 設計判断 → 「なぜ普通のやり方をしていないのか」を16項目。触る前に読むと事故が減る。 開発と運用 → セットアップ、コマンド、何を変えたら何を検証するか、テストと CI の考え方。
