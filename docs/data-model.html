データと認可

モデルは4つしかない。そして認可ルールは全モデルで同じ1本。この単純さは意図して作られたもので、 守らなければならない不変条件でもある。

中心にある1つの規則

すべてのデータは teamId を持ち、認可は「その teamId と同名の Cognito グループに所属しているか」の1問に還元される。

実装としては、4モデルすべてが allow.groupDefinedIn('teamId') を使う。 所有者ベースの認可とグループ認可を混在させないこと。混ぜた時点でこの設計は壊れる。

これを成立させるため、Cognito のグループ名は teamId の値そのものにしてある。 Team モデルは teamId を主キーに宣言し、Amplify が自動採番する id を使わない。 teamId は Lambda が crypto.randomUUID() で採番する（順序性が要らないので ULID の依存を足す理由がない）。

そして全ユーザーが常に、ちょうど1つのチームに属する。 サインアップ時に「自分1人のチーム」が自動生成される。これにより UI から個人モード / チームモードの切り替えが消え、認可ルールも1本に保たれる。

モデル一覧

モデル主キー主なフィールド役割
Team teamId name, inviteCode, inviteCodeExpiresAt, memberCount データの所属単位。個人も「メンバー1人のチーム」
Recipe 自動採番 id teamId, title, url, servings, ingredients, labelIds, memo, imageKey レシピ本体。材料とラベル参照を埋め込みで持つ
Label 自動採番 id teamId, name ラベル。名前のみで色は持たない
UserProfile userId（Cognito の sub） teamId, displayName, theme 表示名・テーマ・所属チーム。Cognito 属性のチーム内向け投影
Ingredient — name, quantity, unit テーブルではない（customType）。Recipe に埋め込まれる

ゲスト用のモデルは存在しない。ゲストのデータは AWS 上に一切保存されない。

UserProfile が必要な理由：クライアントから他ユーザーの Cognito 属性は読めず、 Cognito グループのメンバー一覧も Admin API なしには取得できない。 そのため表示名とチーム所属を DynamoDB 側にも持ち、メンバー一覧を1クエリで引けるようにしている。

認可ルール

モデルルールできること
Team groupDefinedIn('teamId') read / update のみ。作成・削除は Lambda（IAM）だけが行う
Recipe groupDefinedIn('teamId') 同チームなら全操作
Label groupDefinedIn('teamId') 同チームなら全操作
UserProfile ownerDefinedIn('userId').identityClaim('sub')
groupDefinedIn('teamId')		 本人は read / update、同チームは read のみ。
teamId フィールドだけは本人にも read のみ

ここに埋まっている2つの罠

罠 1 — identityClaim('sub') の明示 ownerDefinedIn の既定の claim は cognito:username だが、 UserProfile.userId には sub を入れる設計になっている。 メールをサインイン属性にした場合 Cognito は username として UUID を採番し実質 sub と一致するが、 その一致に依存した実装をしないため claim 側を sub に固定してある。 同じ理由で、Admin API に渡すのは event.userName、UserProfile に入れるのは event.request.userAttributes.sub と、出所を使い分ける。
罠 2 — teamId のフィールドレベル認可 モデル全体の owner 認可は update を許すため、これが無いと本人が teamId を 任意の値に書き換えられる。対応する Cognito グループを持たないのでレシピは読めないが、 他チームのメンバー一覧に自分が現れてしまう。 所属の変更は joinTeam / leaveTeam（IAM）の責務であり、 クライアントからは読めるだけでよい。

チームのライフサイクル

1. サインアップ — 個人チームの自動生成

Cognito の post-confirmation トリガーが実行する（§2.4）。

  1. teamId を生成（crypto.randomUUID()）
  2. Cognito グループ ${teamId} を作成
  3. ユーザーをそのグループに追加
  4. Team レコードを作成（name: 「マイレシピ」, memberCount: 1）
  5. UserProfile を作成（userId: sub, displayName: メールのローカル部）
  6. クライアントが fetchAuthSession({ forceRefresh: true }) で新グループのクレームを取得 これをしないと、作ったばかりのチームのデータが読めない
このトリガーが失敗したら ユーザーの確認自体は既に完了している。結果「確認済みだがチームが無い」ユーザーが生まれ、 以後すべての画面が空になる。トリガー内で例外を投げても確認済み状態は取り消せず体験が悪化するだけなので、 投げない。失敗はログに残し、復旧は下の repairAccount に委ねる。

2. 招待コードによる参加 — joinTeam

この順序に意味がある（§2.5）。

  1. 呼び出し元の sub を event.identity から取得
  2. inviteCode で Team を検索 見つからなければ「無効なコード」
  3. inviteCodeExpiresAt > now を検証 失効なら「期限切れ」
  4. memberCount < 20 を検証 超過なら「満員」
  5. 参加先が現在の所属と同じでないか検証
  6. 新チームの Cognito グループにユーザーを追加 先に権限を付与する。途中で失敗しても新旧どちらかのグループには必ず所属している状態を保つため
  7. 旧チームが1人チームの場合のみ Recipe / Label の teamId を書き換え 旧チームに他メンバーが残る経路が実際にあり、全件移すと残る人からレシピを奪うことになる（実装時に判明した条件）
  8. UserProfile.teamId を更新
  9. 新チームの memberCount をインクリメント
  10. 旧チームの後始末 1人チームなら Team レコードとグループを削除。他にメンバーが居れば memberCount を減らして自分だけグループから外れる（グループごと消える場合は AdminRemoveUserFromGroup を呼ばない）
  11. クライアントが fetchAuthSession({ forceRefresh: true }) → /recipes へ

3. 離脱 — leaveTeam

離脱者はレシピを一切持ち出さない（確定事項）。

  1. 新しい個人チーム（teamId・Cognito グループ・Team レコード）を作成
  2. ユーザーを新グループに追加
  3. UserProfile.teamId を新個人チームへ更新
  4. 旧チームの memberCount をデクリメント
  5. 結果が 0 なら旧チームの Recipe / Label を全削除し、Team とグループを削除
  6. 旧 Cognito グループからユーザーを削除
UI 側の必須要件 離脱ボタンには「レシピはチームに残り、あなたの手元には残りません」と明示する確認モーダルを置く。 これが無いと、誤操作で自分のレシピを失ったという事故が起きる。

4. 自己修復 — repairAccount

すべてのサインイン後に、クライアントは自分の UserProfile の存在を確認する。 無ければこれを呼ぶ。上の2つの中断状態から回復するための仕組み。

  1. UserProfile が無ければ、サインアップと同じ手順で個人チームを新規作成 post-confirmation が失敗したケースの救済
  2. UserProfile はあるが対応する Cognito グループに所属していなければ、グループへ追加
  3. UserProfile.teamId 以外のグループに所属していれば、そこが中断した joinTeam の旧チーム。 1人チームなら残った Recipe / Label を現在のチームへ移送して畳み、他にメンバーが居るならグループから外れるだけにする

3 の検出に所属グループの列挙（AdminListGroupsForUser）を使うのは、 旧チームの teamId を他に知る手がかりが無いため。Recipe を全件走査しても、 Lambda から見える範囲には他人のチームのデータも含まれ、どれが「自分の旧チーム」か判別できない。

招待コードの仕様

形式大文字英数8桁。紛らわしい 0 O 1 I L を除外し、ABCD-2345 のようにハイフン区切りで表示。UUID は口頭・手入力で伝達できないので使わない
有効期限発行から1時間
発行者メンバー全員（チーム内にロールの概念が無いため）
再発行Team.inviteCode は1フィールドなので、再発行すれば旧コードは自動的に無効
照合Team の inviteCode セカンダリインデックス（クライアントからは読めない）
有効期限に DynamoDB の TTL を使ってはならない TTL 削除は best-effort であり、期限到達から最大48時間削除が遅れる。 TTL に頼ると期限切れコードが2日間有効なままになる。 Lambda 側で inviteCodeExpiresAt > now を明示的に比較することが唯一の正解。

参照整合性（ラベル削除）

Recipe.labelIds は ID の配列で、外部キー制約を持たない。3段構えで担保する。

  1. 削除の確認モーダルに「N件のレシピからこのラベルが外れます」と件数を表示 クライアントに全レシピがあるので即座に数えられる
  2. 削除実行時、該当レシピの labelIds から当該 ID を除く更新をまとめて発行
  3. 読み込み時に、存在しない labelId は無視する これが最終防衛線。2 が途中で失敗しても UI 上の不整合は発生しない

トライアル制限（ゲストのみ）

対象上限
レシピ3件
ラベル3件
1レシピあたりの材料10個
  • 制限は「累計」ではなく「同時保有数」。1件削除すれば1件作れる（累計制は「消したのに作れない」となり試用の妨げにしかならない）
  • 登録ユーザーには一切の上限を設けない
  • 既に材料10個を持つレシピの編集は許可する（保存時に個数が増えていなければ通す）
  • 上限到達は入力を始める前に伝える。「新規作成」ボタンを無効化し、その場に登録導線を出す。保存時の例外は本来到達しない経路の保険
  • 通知に window.alert() は使わない（テーマが適用されず、登録への導線ボタンも置けない）

ゲストデータの引き継ぎ

ゲストの localStorage にはサーバーの Recipe と同じ形でデータを持つ。 形を揃えることで、引き継ぎ処理が単純なループで済む。

  1. サインアップ → post-confirmation が個人チームを作成
  2. fetchAuthSession({ forceRefresh: true }) で新グループのクレームを取得 ⚠️ この順序を守らないと、まだ権限のないトークンで書き込むことになり全て Unauthorized になる
  3. UserProfile の存在確認（無ければ repairAccount）
  4. 先に Label を作成し、ローカル ID → サーバー ID の対応表を作る 順序を逆にすると、ラベルが全て外れたレシピが出来上がる
  5. レシピの labelIds を置換して登録
  6. 全件成功してから localStorage をクリア
失敗しても壊れない工夫

3件中2件成功して通信が切れる事態は普通に起こる。

  • 全件成功するまで localStorage をクリアしない
  • 各アイテムに印を立て、印は1件ごとに保存する（まとめて最後に書くと、途中で切れた分が次の試行で二重登録される）
  • ラベルの印は boolean ではなく引き継ぎ先のサーバー ID（migratedId）。boolean だと再試行で対応表を作れず、ラベルの外れたレシピが登録される
  • 失敗時は「取り込みに失敗しました。再試行」を表示し、黙って破棄しない

新規登録とサインインで扱いを変える

状況挙動
新規サインアップ確認なしで自動取り込み。完了後に「ゲストで作成した3件を取り込みました」とトースト
既存アカウントへのサインイン確認モーダル。「追加しない」を選んだ場合のみ localStorage を破棄

登録直後は連続性への期待が最も高くダイアログは邪魔にしかならない一方、 既に多数のレシピを持つ家族チームに試し打ちのダミーが黙って混入するのは防ぐ必要がある。 一貫性より実際の期待値を優先した非対称な扱い。（§5.5）

既知の制約

  • Cognito のグループ数上限（既定 10,000／緩和申請可）がチーム総数の上限になる
  • 検索は漢字とかなの揺れを吸収できない（「玉ねぎ」と「たまねぎ」）。形態素解析辞書が必要になるため v1 の対象外。全角/半角・カタカナ/ひらがな・大文字小文字は吸収する
  • レシピが数千件規模になると初回ロードが重くなる。その時は検索インデックスを足す（スキーマの変更は不要）
