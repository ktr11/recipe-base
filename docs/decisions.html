recipe-base 設計ガイドレシピ保存・家族共有アプリ / Next.js + AWS Amplify Gen 2

概要 構成と動き データと認可 設計判断 開発と運用

なぜこうなっているのか

このアプリには「一見すると間違いに見えるが、実は正しい」箇所がいくつもある。 それらは AWS 側の制約や、実装中に実際にぶつかった問題への対応として選ばれたもの。 コードに手を入れる前に読むと、善意で壊すことを避けられる。

読み方 各項目は「採った案 / 素直な案 / なぜ却下したか / 何を諦めたか」の形で書いてある。 「何を諦めたか」が空でない項目は、状況が変われば再検討の余地がある。

データの持ち方

1. ゲストのデータを AWS に保存せず localStorage に置く

素直な案
Cognito の未認証 Identity（allow.guest()）で DynamoDB に保存する。当初の要件定義にもそう書かれていた
却下の理由
Amplify Data の allow.guest() は所有者単位の分離ができない。owner フィールドは User Pool のユーザーにしか紐づかず、Identity Pool の未認証 ID では機能しない。素直に実装すると世界中の全ゲストが互いのレシピを閲覧・編集・削除できる公開テーブルになり、「3件まで」のカウントも他人のデータを含んで破綻する。クライアント生成の guestId でフィルタする案はサーバー側で強制されず、DevTools から他人のデータが全部読める
実装
backend.ts で allowUnauthenticatedIdentities = false。未認証 Identity 自体を発行せず経路ごと塞いである
諦めたもの
ゲストのデータは端末を変えると引き継げない。ただしトライアルに求められる価値は「本登録前に触れること」であってクラウド永続化ではない。副次的な利点として、認可ルールが「認証ユーザーだけ」を考えればよくなり大幅に単純化した
design.md §5.1

2. 材料を別テーブルにせず Recipe に埋め込む

素直な案
Ingredient モデルを作り Recipe と 1対多で関連づける
却下の理由
  • 材料名の部分一致検索はどのみちクライアント側で行うので、別テーブルにして得られる検索上の利点がない
  • レシピ編集のたびに子レコードの差分計算が必要になり、しかもアトミックに保存できない。通信が切れると材料だけ半分更新された状態が残る
  • 材料は並び順に意味がある。別モデルでは order フィールドの手動管理が要る
埋め込みなら、レシピの保存は常に1回の書き込みで完結する
諦めたもの
材料単位での集計クエリ（「玉ねぎを使うレシピ数」等）はサーバー側でできない
design.md §1.4

3. ラベルを中間テーブルにせず ID 配列で持つ

素直な案
RecipeLabel 中間モデルを定義する（Amplify Gen 2 は manyToMany を廃止しているので自前定義になる）
却下の理由
一覧取得がネストクエリになり N+1 を踏む。全件をクライアントに載せる方針と特に相性が悪い
諦めたもの
参照整合性が保証されない。対策として、読み込み時に存在しない labelId を無視する処理を最終防衛線に置いてある
design.md §1.4 / §1.6

検索と表示

4. 検索をサーバーではなくクライアントで行う

素直な案
GraphQL のフィルタでサーバー側に絞り込ませる
却下の理由
要件の「材料名の部分一致検索」は、DynamoDB がサーバー側で効率的に実行できない操作。contains フィルタは存在するが実体は「全件読んでから捨てる」動作でインデックスが効かない。加えて日本語の表記ゆれも DynamoDB 側では吸収できない
採った案
チームのレシピ全件をクライアントに読み込み、メモリ上で絞り込む。キー入力ごとの通信がゼロなので体感が即座。家族利用ではレシピは数十〜数百件で1クエリに収まる
諦めたもの
数千件規模になると初回ロードが重くなる。その時点で OpenSearch 等の検索インデックスを追加する移行になるが、スキーマは変更せずに済む
design.md §1.5

5. サーバーコンポーネントでデータを取得しない

素直な案
App Router なのだから /recipes の初期表示はサーバー側で取得し initialRecipes として渡す
却下の理由
この案は当初設計書に採用として書かれていたが、実装が進んだ段階で撤回した。消えるのは初回のスピナーだけで転送量は変わらず、そのために AmplifyRepository のサーバー版という第2実装を恒久的に保守することになる。ゲストの画面は原理的にサーバーレンダリングできない（データが localStorage にある）ので、初期描画の経路も2本になる
より根本的には
このアプリは実質「Next.js の上に載った SPA」であり、App Router のサーバー取得の恩恵をほとんど受けない。/recipes だけ SSR に戻すのは局所的な例外を作る動きになる
ただし残したもの
ssr: true（Cookie へのトークン保存）と createServerRunner。用途は /team を守る middleware で、これが無いとサーバー側が常に「未認証」と判定してしまう
design.md §3.4

6. リアルタイム同期（observeQuery）を使わない

採った案
マウント時の取得＋タブフォーカス復帰時（visibilitychange）の再取得
却下の理由
observeQuery は常時 WebSocket 接続を張る。家族利用で「同時刻に別々の端末で編集し続ける」状況は実際には発生せず、その鮮度要求に対して割に合わない
諦めたもの
他メンバーの変更が即座には反映されない。不足を感じた時点で移行でき、その際スキーマは変更不要
design.md §3.5

認証とチーム

7. 全ユーザーが必ず1つのチームに属する（個人＝1人のチーム）

素直な案
「個人のレシピ」と「チームのレシピ」が併存し、UI でモードを切り替える
却下の理由
読み取り経路が2本になり、認可ルールが分岐する。所有者ベースの認可とグループ認可が混在した時点でこの設計は壊れる
効果
認可ルールが1本に統一され、UI から個人/チームの切り替えが消えた
design.md §0 / §1.2

8. Cognito のグループ名を teamId の値そのものにする

理由
allow.groupDefinedIn('teamId') は「teamId フィールドの値と同名のグループに所属しているか」を見る。グループ名と teamId が一致していなければこのルールが成立しない
副作用
Team モデルは teamId を主キーに宣言し、Amplify が自動採番する id を使わない。採番は Lambda の crypto.randomUUID()（順序性が不要なので ULID の依存を足す理由がない）
design.md §1.2

9. チーム参加を Lambda で処理する（クライアントから照合しない）

理由
招待コードを入力する人は、まだそのチームのメンバーではない。したがってクライアントから Team レコードを読んでコードを照合することが原理的にできない（読めるなら誰でも全チームのコードを列挙できてしまう）。加えて Cognito グループの作成・所属変更は Admin API でクライアントからは実行できない
これは異常な構成ではない
Admin API の "Admin" は「人間の管理者が使う」ではなく「開発者側の信頼された資格情報が必要」の意味で、サーバー側から呼ぶことが設計上の想定用途。避けるべきは「ブラウザから Admin API を叩ける」構成であり、ここではクライアントは認証必須のミューテーションしか呼べない
design.md §2.1 / §2.2

10. Cognito のカスタム属性を一切使わない

素直な案
テーマや所属チームを custom:theme のようなカスタム属性に持つ
却下の理由
User Pool のスキーマは作成時に凍結される。カスタム属性を後から追加するにはプールの作り直し＝全ユーザー消滅が必要。「テーマ以外の設定が今後一切増えない」という賭けに負けたときの代償が大きすぎる
採った案
ユーザー単位の情報はすべて DynamoDB の UserProfile モデルで扱う
design.md §6.2

11. 招待コードの有効期限を DynamoDB の TTL で判定しない

却下の理由
TTL 削除は best-effort であり、期限到達から最大48時間削除が遅れる。TTL に頼ると期限切れコードが2日間有効なままになる
採った案
Lambda 側で inviteCodeExpiresAt > now を明示的に比較する。TTL は掃除用途としてのみ併用可
design.md §2.3

12. 招待コードに UUID を使わず、紛らわしい文字を除いた8桁にする

理由
招待コードは口頭や手入力で家族に伝えられる必要がある。UUID はその用途に耐えない。0 O 1 I L を除外した文字セットを使い、ABCD-2345 のように区切って表示する
design.md §2.3

13. 離脱者はレシピを一切持ち出さない

理由
「誰が作ったレシピか」を持たない設計なので、持ち出す範囲を定義できない。チームに残す方が家族の運用実態に合う
必須の緩和策
離脱ボタンには「レシピはチームに残り、あなたの手元には残りません」と明示する確認モーダルを置く。これが無いと誤操作でレシピを失う事故が起きる
design.md §2.6

実装中に判明して形が変わったもの

14. Cognito 操作の IAM ポリシーを専用スタックに切り出す

何が起きたか
postConfirmation の実行ロールに User Pool の ARN を参照するポリシーを直接付けたところ、 UserPool → trigger → Lambda → 実行ロール → ポリシー → UserPool という循環が auth スタック内に閉じ、 CloudFormation がデプロイを拒否した（実際に CloudformationResourceCircularDependencyError で失敗）
対応
backend.createStack('CognitoGroupAccess') でポリシー専用スタックを作り、そこから両 Lambda の実行ロールにアタッチする。auth スタックはポリシースタックを一切参照しないので輪が閉じない
この分離が効く理由
権限範囲を広げる妥協（cognito-idp:* や Resource: "*"）をせずに済む。付与しているのは 5 つのアクションだけで、対象 User Pool の ARN に限定してある
design.md §2.2 / amplify/backend.ts

15. postConfirmation に resourceGroupName: 'auth' を指定する

理由
この関数は auth のトリガーでありながら data へのアクセスを必要とする。既定のスタック配置のままだと auth → function → data → auth の循環参照になりデプロイできない。auth スタックに同居させることで解消する
design.md §2.2

16. Lambda で event.info.fieldName を読まない

何が起きたか
aws-lambda の AppSyncResolverEvent 型は info.fieldName を持つが、 Amplify が生成する直接 Lambda リゾルバは payload の直下に fieldName を置き、info を渡さない。 型を信じて書いた結果、全ミューテーションが「Cannot read properties of undefined」で落ちた
対応
payload.fieldName ?? payload.info?.fieldName の順で読み、どちらも無ければ payload のキー一覧を添えて例外を投げる。 次に形が変わったとき、統合テストの1往復（sandbox デプロイを含む）を無駄にしないため
amplify/functions/team/handler.ts

17. joinTeam のデータ移送を「旧チームが1人だった場合」に限る

当初の想定
「参加する人の旧チームは必ず1人チーム」という前提で、旧チームのレシピを全件新チームへ移す設計だった
実装時に判明したこと
家族チームに属するメンバーが別のチームへ移る経路が実際にある。その場合に全件移すと、旧チームに残るメンバーからレシピを奪うことになる
対応
移送は旧チームが1人だった場合に限る。持ち出さない扱いは離脱（項目13）と共通の方針
design.md §2.5

18. UserProfile.teamId にフィールドレベル認可を足す

当初の弱点
モデル全体の owner 認可が update を許すため、本人が teamId を任意の値に書き換えられた。 対応する Cognito グループを持たないのでレシピは読めないが、他チームのメンバー一覧に自分が現れる
対応
teamId だけ読み取り専用にし、書き込みを Lambda（IAM）に限定した。所属の変更は joinTeam / leaveTeam の責務であり、クライアントには読めれば足りる
design.md §1.7

作り方に関する判断

19. トライアル上限の強制を Repository 層に置く

却下した置き場所
コンポーネントやフックでの判定
理由
新しい作成経路（複製機能・インポート等）を追加した人がチェックを書き忘れるのが典型的な壊れ方。 Repository 層に置けば、どの経路から作成しても必ずこの1点を通る
役割分担
強制は LocalStorageRepository、表示（「残り2件」等）は useTrialLimits()。 後者は判定の責任を持たない。AmplifyRepository は制限を一切持たない
design.md §4.2

20. ゲストと登録ユーザーで同じ画面・同じルートを使う

素直な案
/trial/recipes のようなゲスト専用ルートを設ける
却下の理由
レシピ UI 一式を2系統保守することになり、片方だけ修正して挙動がズレる事故が確実に起きる
採った案
同一ルートを共有し、データ層（RecipeRepository）だけを差し替える
design.md §3.3

21. テーマの「真実」を localStorage に置く

問題
サーバーに保存したテーマは初回描画に間に合わない。Next.js が HTML を返す時点でユーザーのテーマは不明なので、 素直に実装すると「既定テーマで一瞬描画 → 取得後に切り替わる」フラッシュが必ず起きる。ダークテーマ利用者には真っ白な画面が一瞬光る
唯一の対策
<head> 内のブロッキングなインラインスクリプトで localStorage を読み、描画前に <html data-theme> を書く。 <html suppressHydrationWarning> とセットで機能する
サーバー保存の位置づけ
UserProfile.theme は「別端末への同期用の控え」。読み込みで1クエリ増えるが、描画は既に完了しているので体感コストはゼロ
design.md §6.2

22. 数値にならない分量（「適量」「少々」）を許容する

理由
日本のレシピでは 適量 少々 ひとつまみ が頻出し、数値化もスケーリングもできない
設計
quantity を null 可とし、null の材料はスケーリング対象外としてそのまま表示する。 単位は候補付きの自由入力（完全な固定ドロップダウンにすると パック 缶 房 などの裾野が広すぎて必ず不足する）
やらないこと
分数変換（大さじ1/2 等）は v1 では実装しない。単位ごとの丸め規則が必要になり複雑さが跳ね上がるため、料理する人の判断に委ねる。表示は小数第1位で四捨五入し末尾の 0 を落とす
design.md §6.4

23. バックエンド CI を既定では PR で走らせない

問題
認可の統合テストはデプロイ済みの実バックエンドを相手にする。価値は高いが、CI で毎回サンドボックスをフルデプロイ（5〜7分）すると AWS 料金と CI 時間が積み上がる
採った案
PR では backend-ci ラベルを付けた時だけ実行し、main への push では保険として必ず実行する。 常設の ci サンドボックスを使い回し、スキーマを変えた PR の時だけ使い捨ての pr-<番号> をデプロイして破棄する
ラベル opt-in だけにしない理由
付け忘れで検証が抜ける。認可テストは本プロジェクトで最も重い失敗（他人の家族のレシピが見える）を守るテストであり、opt-in の裏に隠してはならない
design.md §10.4

意図的に作っていないもの（v1 スコープ外）

以下は忘れているのではなく、除外すると決めたもの。聞かれない限り実装も提案もしない。

項目見送りの理由
レシピ画像 S3 の追加とチーム単位のパス認可の設計が増える。加えてlocalStorage（上限 約5MB）と致命的に相性が悪く、Base64 で持つと写真2〜3枚で枯渇する。ゲストに画像を許すと S3 への未認証書き込みが必要になり、項目1で回避した問題が再燃する。Recipe.imageKey フィールドだけ予約してある
チーム内のロール（管理者/一般）とメンバーの追放家族単位の利用で権限差を設ける必要がない
複数チームへの同時所属「1ユーザー＝1チーム」が認可ルールを1本に保つ前提になっている
リアルタイム同期項目6
i18nUI は日本語のみ
ソフトデリート / ゴミ箱削除は確認モーダル＋物理削除
E2E テスト（Playwright）価値があるのは「ゲストで作成 → 登録 → 引き継ぎ」の1本だけだが、CI で Cognito のメール確認コードを受け取る仕組みが必要になり投資に見合わない
UI のスナップショットテスト見た目を変えるたびに更新するだけの作業になり、バグを検出しない
