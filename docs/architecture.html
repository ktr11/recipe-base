構成と動き

画面を開いてから中身が出るまでに何が起きるか、コードのどこがその責任を持っているか。

いちばん重要な構造：保存先の差し替え

このアプリの構造で最初に理解すべきなのは、ゲストと登録ユーザーが同じ画面を使い、 違うのはデータ層だけという点。

画面コンポーネント（src/app/, src/components/） データがどこに保存されるかを一切知らない
▼ getRepository() がここで1回だけ分岐する ▼
RecipeRepository（インターフェース） listRecipes / getRecipe / createRecipe / updateRecipe / deleteRecipe
listLabels / createLabel / deleteLabel
LocalStorageRepository ゲスト。トライアル上限の強制もここ
AmplifyRepository 登録ユーザー。teamId の付与と型変換を担う

分岐している場所は src/repositories/index.ts の getRepository() 1箇所だけ。 判定は「fetchAuthSession() がトークンを持っているか」で、 ゲストは AWS にアクセスしないのでトークンを持たない。

なぜ別ルートにしないのか /trial/recipes のような専用ルートを作ると、レシピ UI 一式を2系統保守することになる。 片方だけ直して挙動がズレる事故が確実に起きるため採用していない。（§3.3）

インターフェースは localStorage 側が同期的に処理できる場合でも すべて Promise を返す。契約が実装の都合で分かれると、 呼び出し側が実装を意識することになり、差し替え可能である意味が無くなるため。

ページを開いたときの流れ

  1. <head> のインラインスクリプトがテーマを確定する ThemeScript。localStorage をブロッキングで読み、描画前に <html data-theme> を書く。これをしないとダークテーマ利用者に白画面が一瞬光る（§6.2）
  2. ConfigureAmplify が Amplify.configure(outputs, { ssr: true }) を実行 ssr: true により認証トークンが localStorage ではなく Cookie に保存される。middleware がサーバー側で認証を判定できるのはこのため
  3. useAuth() がゲストか登録ユーザーかを解決する 解決するまではゲスト扱い。「まだ不明な段階でうっかり無制限の UI を見せる」より安全側に倒している。Hub でサインイン/サインアウトも購読しており、共通ナビが古い状態のまま残らない
  4. useRecipes() が Repository からレシピとラベルを読む マウント時に取得。getRepository() がゲスト/登録ユーザーを判定して実装を返す
  5. 絞り込み・並べ替え・スケーリングはすべてブラウザ内で完結 通信ゼロ。src/lib/recipes/ の純粋関数（filterRecipes / sortByUpdatedAtDesc / スケーリング）が担当する

データの鮮度をどう保つか

リアルタイム同期（observeQuery）は使っていない。代わりに2つのタイミングで取り直す。

  • 画面をマウントしたとき — クライアント遷移で戻った場合もフックが再マウントされるので取得される
  • タブにフォーカスが戻ったとき — visibilitychange が visible になった時のみ。実際にこれが埋めるのは「タブを開いたまま放置して戻ってきた」場合
  • 自分の変更は保存後の reload() で反映する

observeQuery は常時 WebSocket 接続を張る。家族利用で「同時刻に別々の端末で編集し続ける」状況は実際には起きないため、その鮮度要求に対して割に合わない。必要になった時点で移行でき、その際スキーマの変更は要らない。（§3.5）

サーバーサイドでデータを取らない

App Router を使っていながら、レシピの取得にサーバーコンポーネントを使っていない。これは検討した上での結論で、設計書 §3.4 に記録がある。

理由内容
効果が小さい全件をクライアントに載せて絞り込む方針（§1.5）なので、サーバーで取っても同じ量が同じ経路でブラウザへ渡る。消えるのは初回のスピナーだけ
実装が二重化するAmplifyRepository はブラウザのグローバルセッション前提。サーバー版はリクエスト文脈から client と teamId を注入する別実装になり、契約テストの軸も増える
恩恵が1画面だけ/recipes の初回描画のみ。/recipes/new・/recipes/[id]・/labels はクライアント取得のまま残る
ゲストは原理的に不可データが localStorage にあるためサーバーレンダリングできない。初期描画の経路が恒久的に2本になる
それでも残しているもの ssr: true（Cookie へのトークン保存）と createServerRunner は残してある。 用途はデータ取得ではなく /team を守る middleware。サーバーは localStorage を読めないため、 既定設定のままでは middleware が常に「未認証」と判定してしまう。

将来レシピが増えて初回ロードが重くなった場合の答えは、SSR ではなく 検索インデックス（OpenSearch 等）の追加である。その時もスキーマは変えずに済む。

middleware で保護しているのは /team だけ（src/middleware.ts の matcher）。 他はすべてゲストで機能するため、middleware を広く掛けるとゲストの導線を塞いでしまう。 /settings はページ内で認証セクションを出し分けるだけでよく、対象外にしてある。 テーマ設定が localStorage 駆動でゲストでも完全に動くため、ここを閉じるとゲストがダークテーマを選べず不自然になる。

Lambda を呼ぶ操作

クライアントから直接 DynamoDB を触れない操作は、AppSync のカスタムミューテーション経由で Lambda が行う。窓口は src/lib/team/api.ts。

操作なぜ Lambda が必要か
joinTeam招待コードを入力する人はまだそのチームのメンバーではない。クライアントから Team を読んで照合することが原理的にできない（読めるなら誰でも全チームのコードを列挙できる）
leaveTeamCognito グループからの除外・新しい個人チームの作成が Admin API
issueInviteCodeコードの生成と有効期限の付与をサーバーで確定させる
repairAccountグループの作成・所属変更・所属の列挙が Admin API
忘れやすい点 参加と離脱の後は必ず fetchAuthSession({ forceRefresh: true }) を呼ぶ。 所属の変更は発行済みトークンに載らないため、取り直すまで新しいチームのレシピが1件も読めない （逆に、抜けたはずのチームのレシピが見え続ける）。

ロジックの置き場所の原則

「どこに書くか」の判断は、この2つに集約されている。

強制するものは Repository 層へ トライアル上限の判定は LocalStorageRepository の中にある。 コンポーネントやフックだけに置くと、新しい作成経路（複製・インポート等）を足した人が チェックを書き忘れる。Repository に置けばどの経路も必ず1点を通る。
判断のいらないものは純粋関数へ 検索・スケーリング・ラベル ID の付け替え・招待コード生成は AWS もブラウザも要らない純粋関数に切り出してある。 結果として、壊れると痛い箇所がそのまま単体テストの対象になっている。

なお useTrialLimits() は「残り何件か」を返すだけで、判定の責任を持たない。 表示専用と強制を意図的に分けている。（§4.2）
