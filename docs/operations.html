開発と運用

手元で動かす手順、何を変えたら何を検証するか、テストと CI の考え方。

セットアップ

前提：Node.js 20 以上、pnpm、AWS 認証情報が設定済み（aws sts get-caller-identity で確認できる）。

pnpm install

次にバックエンドを自分専用の AWS 環境にデプロイする。

pnpm exec ampx sandbox
このコマンドは実際に AWS リソースを作成する Cognito User Pool・AppSync API・DynamoDB テーブル・Lambda が実際に作られ、課金対象になる。 実行したまま常駐させると amplify/ の変更を検知して自動で再デプロイする。 片付けは pnpm exec ampx sandbox delete。

接続情報は amplify_outputs.json に出力される。このファイルは接続先が環境ごとに異なるため Git 管理外で、フロントエンドの起動に必要になる。 つまり一度もサンドボックスをデプロイしていない環境では pnpm dev が動かない。

別のターミナルで：

pnpm dev   # http://localhost:3000

コマンド内容AWS

pnpm build本番ビルド（TypeScript の型検査を含む）不要

何を変えたら何を検証するか

変更した箇所実行するもの
フロントエンド（src/） pnpm build（型検査を含む）
バックエンド（amplify/） pnpm exec tsc --noEmit -p amplify/tsconfig.json と pnpm build
認可ルール・スキーマ 上記に加えて pnpm test:integration、および PR に backend-ci ラベル
見落としやすい依存関係 バックエンドを変更した場合も pnpm build を通すこと。 amplify/ はルートの tsconfig から除外してあるが、src/ が amplify/data/resource の型を参照している。スキーマの変更はフロントエンドのビルドを壊し得る。

なお $amplify/env/* の型はデプロイ時にのみ生成されるため、 一度も ampx sandbox を実行していない環境ではバックエンドの型検査が通らない。

テストの方針

テストは2種類に分け、目的も実行環境も分離してある。 混ぜると、AWS への接続が必要なテストのせいで単体テストが遅くなり、誰も実行しなくなる。

種別コマンド対象実行環境
単体テストpnpm test純粋なロジックローカル完結。AWS 不要
統合テストpnpm test:integration認可ルールデプロイ済み sandbox に対して実行

契約テスト — このプロジェクト特有の形

LocalStorageRepository と AmplifyRepository は 同じインターフェースを実装し、同じ振る舞いをしなければならない。 そのためテストは片方ずつではなく、両実装が満たすべき契約として書かれている。 

describe.each([
  ['LocalStorageRepository', () => new LocalStorageRepository()],
  ['AmplifyRepository',      () => new AmplifyRepository()],
])('%s', (_name, create) => { /* 共通の契約 */ })

実体は tests/unit/support/recipe-repository-contract.ts。 先に契約を書いたから自然にこの形になった。動いているコードに後からテストを書く順序では、 実装がテストしやすい形に寄る力が働かず、この構造は現れない。

単体テストの対象

対象要点
トライアル制限の判定3/3/10 の境界。削除後に再作成できること（累計ではなく同時保有数）
検索フィルタ・正規化全角/半角・カタカナ/ひらがなの吸収。複数条件の AND
x人前スケーリングquantity: null をスケールしない分岐、小数の丸め
ラベル ID の付け替え移行時にラベルが外れないこと。印による冪等性
招待コードの生成除外文字（0 O 1 I L）が出現しないこと

この一覧は、設計書が「壊れやすい」と名指しした箇所とほぼ一致している。それは偶然ではない。

認可の統合テスト — 最も価値が高いテスト

groupDefinedIn による認可が誤っていた場合の帰結は「他人の家族のレシピが見える」であり、影響が最も重い。 そしてこれはモックでは何も証明できない — 実際にデプロイされた AppSync にリクエストを投げるしかない。

検証するシナリオの主眼は「できないこと」の確認にある。

  • チーム A のユーザーが、チーム B のレシピを list で取得できない
  • チーム A のユーザーが、チーム B のレシピを ID 直指定で get できない
    一覧に出ないことと、取得できないことは別の保証である
  • チーム A のユーザーが、チーム B のレシピを更新・削除できない
  • 同一チームの別ユーザーが、互いのレシピを編集できる
  • チームに所属しないユーザーが、Team を読んで招待コードを列挙できない
  • 有効期限切れの招待コードで joinTeam が失敗する

CI の実行モデル

ワークフロー実行条件内容AWS
ci.yml すべての PR と main への push lint / pnpm build（型検査含む）/ 単体テスト 不要
backend.yml PR は backend-ci ラベルが付いた時だけ／main への push は必ず／手動実行も可 バックエンドの型検査 + 認可の統合テスト 必要

サンドボックスの扱いには、守るべき不変条件がある。

「常設 ci サンドボックスは常に main のスキーマを反映する」
  • 既定では常設の ci サンドボックスを使い回す。スキーマ差分が無ければ ampx sandbox --once は実質 no-op で、フルデプロイ（5〜7分）を丸ごと省ける
  • スキーマ（amplify/**）を変更した PR の時だけ、隔離した使い捨て pr-<番号> をデプロイし、末尾で破棄する。ci（＝main 状態）を汚さないため、未マージの PR が何本あっても常設サンドボックスは main のスキーマのまま保たれる
  • main への push が毎マージで ci を最新スキーマへ収束させ、この不変条件を維持する

したがって認可やスキーマを触った PR は backend-ci ラベルを付けて統合テストを通してからマージする。 手元で pnpm test:integration を通してから push できればなお良い。

コミットの粒度

意味のある単位ごとにコミットし、混ぜない。とりわけ ツールが生成した雛形は未修正のままコミットするという規約がある。 

create-next-app を実行                → commit
npm create amplify を実行             → commit
auth/resource.ts を設計に合わせて修正 → commit

こうすると次のコミットの差分が「自分たちの設計判断」だけになり、 レビューで生成物と判断が混ざらない。コミットメッセージは日本語。

設計を変えるときの必須手順 コードだけでなく docs/design.md も併せて更新する。 設計書とコードが食い違った時点で、この資料群の価値は失われる。

この解説サイトの公開について

このサイトは docs/ 配下の静的 HTML で、GitHub Pages が main ブランチの /docs フォルダを直接配信している。 ビルドステップは無い。HTML を編集して main に入れれば、数十秒後に反映される。

  • ページを追加したら、各ページのナビゲーション（nav.site-nav）にもリンクを足す
  • スタイルは docs/assets/site.css の1枚だけ。外部 CDN・外部フォントには依存していない
  • docs/.nojekyll は Jekyll による処理を止めるための空ファイル。消さないこと
